Phase 2 · Foundations

Mathematics Foundations

This is the phase ML Engineer interviews actually probe — not to make you prove theorems, but to see if you understand why a model behaves the way it does.

Linear Algebra

SubtopicsScalars, vectors, matrices, tensors, matrix multiplication, transpose, inverse, eigenvalues/eigenvectors (intuition).
Why it mattersEvery dataset is a matrix, every model's weights are matrices/tensors, and PCA runs directly on eigenvectors.
Interview focus"What does the inverse of a matrix represent?" / "Why can't every matrix be inverted?" — conceptual, not computational.

Calculus

SubtopicsDerivatives, partial derivatives, chain rule, gradients, optimization intuition.
Why it mattersGradient descent — the algorithm training every model in this roadmap — is just "follow the negative gradient."
Practical exerciseCompute the gradient of a simple loss function (e.g. mean squared error for 1 weight) by hand, then verify it numerically in Python.

Probability

SubtopicsRandom variables, probability distributions, conditional probability, Bayes' theorem.
Why it mattersNaive Bayes runs on this directly; every classifier's output is really a probability estimate.

Statistics

SubtopicsMean/median/mode, variance & standard deviation, covariance & correlation, hypothesis testing basics, confidence intervals.
Why it mattersDeciding whether a metric improvement from a model change is real, or just noise, is a statistics question — not an ML one.
What's actually important for ML interviews: gradient intuition, matrix/vector operations, probability distributions, Bayes' theorem, and being able to reason about variance — not proofs, not measure theory, not abstract algebra.
Common mistakeSpending months on pure-math courses before writing any ML code. Learn math alongside Phase 5–7, tied to a concrete model, or it won't stick.
  • Linear algebra essentials 🟢
  • Calculus & gradients 🟢
  • Probability essentials 🟢
  • Statistics essentials 🟢

Phase 5 · Core ML

Core Machine Learning Fundamentals

The vocabulary you'll use in every ML conversation for the rest of your career starts here.

ParadigmWhat it meansPriority
Supervised learningLearn a mapping from labeled inputs to outputs (Phases 6–7).🟢
Unsupervised learningFind structure in unlabeled data (Phase 9).🟢
Reinforcement learningLearn via reward signals from an environment — know the concept, deep RL is a separate specialization.🔵

The concepts that decide whether you understand ML

Features & labelsInputs the model sees vs. the answer it's trying to predict.
Train/val/test splitNever evaluate on data the model has seen — the single most-violated rule by beginners.
Cross-validationK-fold gives a far more trustworthy performance estimate than one split.
Bias vs. varianceUnderfitting (high bias) vs. overfitting (high variance) — the central tension in every model.
RegularizationL1/L2 penalties that deliberately trade a little training accuracy for generalization.
Common mistakeTuning hyperparameters against the test set — this silently turns your test set into a second validation set and inflates your reported performance.

Phase 6 · Classical ML

Regression Algorithms

Predicting a continuous number — the simplest place to build real evaluation instincts before adding complexity.

Linear Regression 🟢Multiple Linear Regression 🟢Polynomial Regression 🟡 Ridge 🟢Lasso 🟢Elastic Net 🟡

Assumptions worth knowing (for Linear Regression)

LinearityRelationship between features and target is approximately linear.
Independence & homoscedasticityErrors are independent, with roughly constant variance across predictions.
No severe multicollinearityHighly correlated features make coefficients unstable and hard to interpret.
MetricWhat it tells you
MAEAverage absolute error, in the target's own units — robust to outliers.
MSE / RMSEPenalizes large errors more heavily; RMSE is back in the target's units.
R²Proportion of variance explained — 0 means "no better than predicting the mean."
Common mistakeReporting R² alone. A high R² can still hide a model that's terrible on the exact cases that matter most (e.g. high-value customers).
Practical exercise: fit plain Linear Regression, then Ridge, then Lasso on the same dataset with a few collinear features — watch how the coefficients change and connect that back to the regularization theory.
  • Linear & multiple regression 🟢
  • Ridge / Lasso / Elastic Net 🟢
  • MAE, MSE, RMSE, R² 🟢
Phase 7 · Classical ML

Classification Algorithms

Predicting a category — where evaluation gets genuinely tricky, especially once classes are imbalanced.

Logistic Regression 🟢KNN 🟡Naive Bayes 🟡SVM 🟡 Decision Trees 🟢Random Forest 🟢Gradient Boosting 🟢 XGBoost 🟢LightGBM 🟡CatBoost 🔵
MetricUse when
AccuracyClasses are roughly balanced — otherwise misleading.
PrecisionFalse positives are expensive (e.g. flagging a legit transaction as fraud).
RecallFalse negatives are expensive (e.g. missing an actual fraud case).
F1-scoreYou need a single number balancing precision & recall.
ROC-AUCRanking quality across all thresholds — less useful under heavy imbalance.
PR-AUCBetter than ROC-AUC when the positive class is rare.
Confusion MatrixAlways look at this before trusting any single metric.
Class imbalance: a fraud model predicting "not fraud" every time can hit 99% accuracy while being completely useless. This is where PR-AUC, class weights, and resampling (Phase 8) become essential, not optional.
Common mistakeDefaulting to accuracy as the headline metric on an imbalanced dataset without even checking the class distribution first.

Practical exercise

TaskTrain Logistic Regression, Random Forest, and XGBoost on the same imbalanced dataset; compare confusion matrices, not just one aggregate metric.
  • Core classification algorithms 🟢
  • Gradient boosting family (XGBoost at minimum) 🟢
  • Full classification metric set 🟢

Phase 8 · Classical ML

Feature Engineering and Model Improvement

This is usually where the real performance gains come from — not swapping algorithms.

Scaling

🟢

Standardization (z-score) vs normalization (min-max) — required for distance/gradient-based models.

Encoding categoricals

🟢

One-hot for low-cardinality, label/target encoding for high-cardinality — with leakage caution on target encoding.

Feature selection

🟡

Removing noisy features improves both performance and interpretability.

Feature importance

🟢

Tree-based importances, permutation importance — first line of model debugging.

PCA

🟡

Dimensionality reduction — useful, but hurts interpretability.

Handling imbalanced datasets

Class weightsCheapest fix — penalize misclassifying the minority class more heavily during training.
Oversampling / SMOTESynthesize minority-class examples — apply only on the training fold, never before splitting.

Hyperparameter tuning

Grid SearchExhaustive — fine for small search spaces.
Random SearchOften finds a near-optimal config faster than grid search on large spaces.
Bayesian optimizationUses past results to choose the next config intelligently (e.g. Optuna) — the production default.
Common mistakeApplying SMOTE before the train/test split — it leaks synthetic near-duplicates of test-set patterns into training.
  • Scaling & encoding 🟢
  • Feature selection & importance 🟢
  • Class weights & SMOTE 🟢
  • Hyperparameter tuning (all 3 methods) 🟢
Phase 9 · Classical ML

Unsupervised Learning

No labels, just structure. Less commonly the whole job, but shows up constantly inside bigger pipelines (segmentation, anomaly flags, visualization).

K-Means 🟢Hierarchical clustering 🔵DBSCAN 🟡 PCA 🟢t-SNE 🔵UMAP 🔵Anomaly detection 🟡
K-MeansFast, simple, needs you to choose K in advance — use the elbow method or silhouette score.
DBSCANFinds arbitrarily-shaped clusters and flags outliers automatically — no need to pre-specify cluster count.
t-SNE / UMAPFor visualizing high-dimensional embeddings in 2D — good for exploration, not for feeding into a downstream model.
Common mistakeTreating t-SNE cluster distances as meaningful — t-SNE distorts global distances by design; only local neighborhoods are trustworthy.
  • K-Means & DBSCAN 🟢
  • PCA / t-SNE / UMAP for visualization 🟡
  • Anomaly detection basics 🟡

CNN intuition

ConvolutionA small filter slides across the image, learning to detect local patterns (edges, textures).
Padding & strideControl output size and how much the filter overlaps as it moves.
PoolingDownsamples feature maps, adding translation tolerance and reducing compute.
Feature mapsEarly layers learn edges; deeper layers learn increasingly abstract shapes.

Common mistakeSkipping data augmentation on a small image dataset, then being confused why the model overfits within a few epochs.

Phase 18 · Production

MLOps

The single biggest differentiator between "trained a model once" and "Machine Learning Engineer." Give this real time.

Why MLOps

The problemModels silently decay — the world changes, users change, and a model frozen at deploy-time drifts further from reality every week.
The ML lifecycleData → train → evaluate → deploy → monitor → retrain — a loop, not a one-time pipeline (see the Phase 0 diagram).
AreaWhat it coversTools
Experiment trackingLogging every run's params, metrics, and artifacts so results are comparable and reproducible.MLflow, W&B
Data & model versioningWhich exact dataset and model version produced a given result — essential for debugging and rollback.DVC, model registry
PipelinesAutomating the data → train → eval → deploy steps so they run reliably and repeatably.Airflow / Prefect-style tools
CI/CD for MLAutomated testing + deployment triggered on code or data changes.GitHub Actions
MonitoringTracking prediction distributions, latency, and errors in production.Logging + dashboards

Drift — the concept every MLOps interview asks about

Data driftThe distribution of incoming input features changes over time (e.g. new customer demographics).
Concept driftThe relationship between features and the target itself changes (e.g. fraud patterns evolve).
ResponseMonitor both, set alert thresholds, and have a retraining trigger/schedule rather than reacting only after complaints.
Common mistakeTreating "deployed" as "done." A model with no monitoring is a silent liability — you find out it broke from a business metric dropping, weeks later.
Practical exercise: track 5 training runs of the same model with different hyperparameters in MLflow, register the best one, and write a short report on what changed and why.
  • Experiment tracking (MLflow/W&B) 🟢
  • Data versioning (DVC) & model registry 🟢
  • CI/CD for ML pipelines 🟢
  • Data drift vs concept drift 🟢
  • Monitoring & retraining triggers 🟢

Avoid The Trap

What NOT to learn initially

The ML ecosystem is huge. Trying to cover all of it before shipping anything is the most common way people burn out and quit.

Mastering every ML framework

scikit-learn + PyTorch covers the overwhelming majority of real work — depth in two beats shallow exposure to ten.

Jumping to LLMs before ML fundamentals

Prompting a model is not the same skill as understanding bias/variance, evaluation, and why a model fails on a specific slice.

Training huge models from scratch

Unnecessary for almost every ML Engineer role. Transfer learning and fine-tuning solve the vast majority of real problems.

Collecting certificates instead of building

A certificate shows you finished a course. A project shows you can actually do the job.

Only watching tutorials

Passive watching feels like progress and isn't — cap tutorial time and spend the rest debugging your own code.

Building only notebooks

A notebook only you can run isn't a portfolio piece. Ship it as a script, an API, or a small app.

Ignoring deployment and MLOps

The gap between "I trained a good model" and "I can ship and maintain one" is exactly what separates candidates in interviews.

Ready Check

If you can do these, you're ready to apply

  • Explain the bias/variance trade-off with a concrete example from your own project.
  • Justify a metric choice (why F1, not accuracy) under questioning.
  • Debug a training run where loss isn't decreasing.
  • Explain data drift vs. concept drift, and how you'd detect each.
  • Wrap a model behind a FastAPI service and containerize it.
  • Walk through one project's architecture, end-to-end, from memory.
  • Explain why you split time series data chronologically, not randomly.
  • Read someone else's PyTorch training loop and explain what it does.

The Golden Rule: "A model in a notebook is a hypothesis. A model in production is an engineering achievement."

ML Engineering keeps evolving — but bias/variance, honest evaluation, and the discipline to monitor what you ship stay useful no matter what tool is trendy next year. Ship something small this week.
