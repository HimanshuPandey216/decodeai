LangChain vs LangGraph

LangChain helps you build AI applications. LangGraph helps you orchestrate AI applications that need memory, state, decisions, loops and control.

So… are LangChain and LangGraph competitors?

No. They solve related but different problems, and in most real applications, they're used together — not instead of each other.

Think of it this way: LangChain is the box of LEGO pieces. LangGraph is the instruction booklet and the control system that decides which piece goes where, in what order, and what happens if a piece doesn't fit.

LangChain provides the pieces

  • Models (LLMs & chat models)
  • Prompts
  • Tools
  • Retrievers
  • Embeddings
  • Agents
  • Structured outputs
  • Document processing
  • Integrations

LangGraph decides the flow

  • What happens first
  • What happens next
  • Which node executes
  • When to branch
  • When to loop
  • What state is remembered
  • When a human should intervene
  • When the workflow should stop

What exactly is LangChain?

LangChain is a framework and ecosystem for developing applications powered by large language models. Click any concept below to see a plain-language definition, an analogy, and a tiny code example.

What exactly is LangGraph?

LangGraph is a framework for building stateful, multi-step, controllable AI workflows and agents. Every concept below is about controlling flow — not adding new capabilities to the model itself.

The same idea, in code

Short, realistic examples — not production code, just enough to see the shape of each framework.

🟢 LangChain

python
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

model = ChatOpenAI(model="gpt-4o-mini")
prompt = ChatPromptTemplate.from_template(
    "Answer the customer question:\n{question}"
)
parser = StrOutputParser()

# LCEL: chain components together with the pipe operator
chain = prompt | model | parser

response = chain.invoke({"question": "Where is my order?"})
print(response)
  • The prompt, model, and parser are independent, reusable components.
  • The | operator wires them into one pipeline (LCEL).
  • .invoke() runs the whole pipeline once, start to finish.
  • There's no persistent state — call it again and it has no memory of the last call.

🔵 LangGraph

python
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    question: str
    answer: str
    needs_retry: bool

def agent_node(state: State) -> State:
    state["answer"] = f"Draft answer for: {state['question']}"
    state["needs_retry"] = "unsure" in state["answer"]
    return state

def check_node(state: State) -> State:
    return state

def route(state: State) -> str:
    return "agent_node" if state["needs_retry"] else END

graph = StateGraph(State)
graph.add_node("agent_node", agent_node)
graph.add_node("check_node", check_node)
graph.add_edge(START, "agent_node")
graph.add_edge("agent_node", "check_node")
graph.add_conditional_edges("check_node", route)

app = graph.compile()
app.invoke({"question": "Where is my order?", "answer": "", "needs_retry": False})
  • State is the shared object every node reads and updates.
  • Each node (agent_node, check_node) is one discrete step.
  • add_conditional_edges decides the next node at runtime, and can loop back to agent_node.
  • The graph is compiled once, then invoked — and can be checkpointed, paused, and resumed.

Do I need LangGraph for RAG?

Usually, no.

This is a straight pipeline — retrieve once, generate once. LangChain's retriever and chain abstractions handle this comfortably, with no branching or memory required.

But here's when LangGraph earns its place: when the pipeline needs to judge its own retrieval and try again.

That "no → rewrite → retrieve again" loop is a cycle, with a decision in the middle. That's precisely the shape LangGraph was designed to express.

The evolution of an "agent"

As requirements get more sophisticated, the right tool shifts from LangChain toward LangGraph — not because one is "better," but because the problem itself changes shape.

Level 1
Simple LLM
User → LLM → Answer. The model just answers. No tools, no memory, no decisions.
Level 2
Tool Calling
User → LLM → Tool → LLM → Answer. The model can reach for one tool mid-answer.
Level 3
Agent
The LLM decides which tool to call, and in what order, instead of following a fixed script.
Level 4
Stateful Agent
The agent remembers previous actions and results, so step 5 can depend on what happened at step 2.
Level 5
Complex Agent Workflow

Modeling a multi-agent system

LangGraph is a natural fit once you have more than one "agent" that need to collaborate on a task.

SUPERVISOR
↓
RESEARCHER
CODER
REVIEWER
↓
OUTPUT

The supervisor node decides which specialist agent runs next, based on the current state — a classic conditional-edge pattern. Each specialist can be as simple or complex as needed.

LangChain and LangGraph are not necessarily alternatives.
LangChain components can live inside LangGraph workflows.

In practice: the RESEARCHER node might use a LangChain retriever, the CODER node might use a LangChain tool-calling agent, and LangGraph is simply the supervisor wiring them together with state and control flow.

Architecture deep dive

For the intermediate/advanced reader: LangGraph is not simply "LangChain with a graph-shaped UI on top." The execution model underneath is genuinely different.

Application
LangChain components
  • Models
  • Tools
  • Retrievers
  • Prompts
  • Agents
LangGraph orchestration
  • State
  • Nodes
  • Edges
  • Conditions
  • Persistence
  • Execution flow

LangChain's composition model (LCEL) is fundamentally a pipeline: data flows through a sequence of components once, from top to bottom, when you call .invoke(). It's excellent for composition, but it wasn't designed around cycles, mid-run pauses, or resuming days later.

LangGraph's execution model is a persistent, resumable state machine: it explicitly tracks a state object, checkpoints it after every node, supports cycles (returning to an earlier node), and can pause indefinitely for a human — then resume from that exact point. That's a different engine underneath, not just a different diagram on top of the same one.
